# Marketplace Analytics

MVP аналитической платформы маркетплейса целиком: синтетический
источник данных, DQ-пайплайн на Spark, витрины в ClickHouse,
ежедневное расписание в Airflow и дашборд в Superset. Слои разбираются
по порядку в разделах «Полный прогон» и «Архитектура» ниже.

## Генератор данных

Генератор моделирует конкретно **маркетплейс с логистикой доставки
через пункты выдачи** (модель в духе Ozon/Wildberries), а не
универсальный e-commerce и не сетевую розницу. У сетевой розницы
(Пятёрочка, Магнит) транзакция принципиально проще — покупка в моменте,
без цепочки shipped→ready_for_pickup→delivered — это не частный случай
данной модели, а другая модель, требующая своей state machine. Генератор
имитирует ежедневную выгрузку `customers` / `orders` / `payments` из
учётной системы (АС) в виде CSV-партиций, с контролируемой инжекцией
DQ-ошибок для тестирования пайплайнов и дашбордов качества данных.

CSV — осознанный выбор, а не недосмотр: генератор имитирует именно
**сырую выгрузку из источника**. Преобразование в Parquet — зона
ответственности отдельного downstream-скрипта, не этого репозитория.

## Быстрый старт

```bash
pip install -r requirements.txt

python generate_data.py \
  --load-date 2026-08-18 \
  --data-dir ./data \
  --customers-count 100 \
  --orders-count 15000 \
  --payments-count 15150 \
  --error-rate 0.01 \
  --payment-deadline-hours 24 \
  --shipping-deadline-hours 48 \
  --delivery-deadline-days 7 \
  --pickup-deadline-days 7 \
  --return-window-days 14 \
  --refund-processing-hours 72 \
  --cancel-before-payment-rate 0.02 \
  --cancel-after-payment-rate 0.01 \
  --return-rate 0.05 \
  --never-order-rate 0.18
```

Все параметры дедлайнов/вероятностей опциональны — значения выше
одновременно являются дефолтами, если их не указывать явно.

Повторный запуск с тем же `--load-date` для того же `--data-dir`
намеренно завершится ошибкой — см. «Контракт партиционирования» ниже.

Чтобы увидеть реальную state machine в действии, запусти генератор
несколько раз подряд с последовательными датами (`--load-date`) —
заказы, не закрытые в один прогон (не оплаченные, не отправленные и
т.д.), будут подхватываться и продвигаться в следующих.

## Полный прогон: от генерации до ClickHouse

Разовый запуск `generate_data.py` выше — только для знакомства с
генератором. Чтобы прогнать весь пайплайн (source → raw →
clean/quarantine → ClickHouse) на реалистичной истории (рампа + плато,
см. `backfill_history.sh`), нужны все слои по очереди.

**1. Зависимости**

```bash
pip install -r requirements.txt
pip install -r requirements-spark.txt   # для transform.py и load_to_clickhouse.py
```

**2. Поднять ClickHouse**

Схема (`clickhouse_schema.sql`) применяется автоматически при первом
же запуске `load_to_clickhouse.py` (`ensure_schema()`) — руками её
создавать не нужно, нужен только сам сервер:

```bash
export CLICKHOUSE_PASSWORD=<придумай-пароль>
docker compose up -d clickhouse
```

Поднимает `clickhouse/clickhouse-server` с пользователем
`analytics_user`/`$CLICKHOUSE_PASSWORD` и базой `marketplace_analytics` (HTTP —
`localhost:8123`, native-протокол для `clickhouse-client` —
`localhost:9000`). См. `docker-compose.yml`.

Host/port/database/user (без пароля — он нигде в репозитории не
хранится) — единый источник правды в `clickhouse_config.json`, общий
для `load_to_clickhouse.py` (дефолты CLI-аргументов),
`run_downstream_pipeline.sh` и Airflow DAG'а (`dags/daily_marketplace_pipeline.py`).

**3. Сгенерировать историю (source-слой)**

```bash
./backfill_history.sh
```

Диапазон дат, форма кривой (рампа + плато) и бизнес-правила —
`growth_config.json`, единый источник правды для этого скрипта,
`run_downstream_pipeline.sh` и Airflow DAG'а; на дефолтах это 95 дней,
2026-06-01 → 2026-09-03. При сбое посреди прогона —
`./backfill_history.sh <день>` (см. комментарий в шапке скрипта).

Помимо объёма, скрипт передаёт `--launch-date`, включающую отдельную
(более быструю, 21 день) динамику `error_rate` — см. «Реалистичная
динамика error_rate» ниже.

**4. Прогнать вниз по пайплайну (raw → clean/quarantine → ClickHouse)**

```bash
./run_downstream_pipeline.sh
```

Пароль ClickHouse берётся из `CLICKHOUSE_PASSWORD` (той же переменной,
что читает `docker-compose.yml`), а если её нет — скрипт спросит его
скрытым вводом. В аргументах командной строки пароль не передаётся:
оттуда он попадает в историю оболочки и в список процессов.

Для каждого дня: `ingest_csv_to_raw.py` → `transform.py` →
`load_to_clickhouse.py`. Загрузка в ClickHouse идемпотентна (см.
«Идемпотентная загрузка в ClickHouse» ниже) — скрипт безопасно
перезапускать, уже загруженные дни просто пропускаются.

И `backfill_history.sh`, и `run_downstream_pipeline.sh` могут идти часами
(генерация + Spark на десятки дней). Обычный foreground-процесс в
SSH-сессии получит `SIGHUP` и оборвётся при закрытии терминала —
запускай в чём-то, что переживает отключение:

```bash
# tmux/screen — можно вернуться и посмотреть прогресс
tmux new -s pipeline
./run_downstream_pipeline.sh
# отключиться: Ctrl+B, затем D; вернуться: tmux attach -t pipeline

# либо nohup + фон
nohup ./run_downstream_pipeline.sh > pipeline.log 2>&1 &
disown
# прогресс: tail -f pipeline.log
```

**Перезагрузить один конкретный день** (например, если подозреваешь
задвоение из-за более раннего сбоя коннектора):

```bash
python load_to_clickhouse.py \
  --load-date 2026-07-28 \
  --force-reload
```

Пароль здесь тоже берётся из `CLICKHOUSE_PASSWORD`; флаг
`--clickhouse-password` остался для разовых ручных запусков.

**Проверить, что реально загружено:**

```bash
docker exec -it analytics-clickhouse clickhouse-client \
  --user analytics_user --password "$CLICKHOUSE_PASSWORD" \
  --query "SELECT load_date, entity, rows, loaded_at FROM marketplace_analytics._load_commits ORDER BY load_date"
```

**5. Дашборд в Superset (опционально)**

Витрины дашборда «Аналитика маркетплейса» — объекты ClickHouse (база
`marketplace_marts`, см. «Семантический слой» ниже), они применяются
сами при загрузке. В Superset остаются только чарты и раскладка;
`superset/apply_review_fixes.py` приводит их к целевому состоянию через
REST API — идемпотентно, с предварительной выгрузкой текущего состояния
для отката. Подробности — в [`superset/README.md`](superset/README.md).

## Архитектура

### Партиционирование и layout на диске

```
data/source/
  customers/load_date=YYYY-MM-DD/customers.csv
  orders/load_date=YYYY-MM-DD/orders.csv
  payments/load_date=YYYY-MM-DD/payments.csv
  _commits/load_date=YYYY-MM-DD/commit.json
```

Каждый запуск генератора — это один батч, привязанный к одной дате
загрузки (`--load-date`). Внутри батча три сущности пишутся в
отдельные Hive-style партиции.

### Контракт для потребителей данных

**Партиция считается доступной для чтения только тогда, когда для
неё существует `_commits/load_date=.../commit.json`.** Если
commit-маркера нет — партиция не готова (или публикация упала
посередине), читать её нельзя, даже если файлы `customers.csv` /
`orders.csv` / `payments.csv` физически на месте.

Это осознанный выбор вместо истинной POSIX-атомарности между
несколькими директориями (которой на файловой системе просто не
существует): вместо неё используется commit-маркер как единственный
источник истины о готовности батча.

`publish_batch()` гарантирует, что для `source_root` в любой момент
времени верно ровно одно из двух:
- все три сущности **и** commit-маркер присутствуют, **или**
- ни одной из них там нет (если что-то упало посередине —
  уже перемещённое откатывается обратно в staging, а не остаётся
  «осиротевшим» без маркера).

`customers`/`orders`/`payments` перемещаются из временной staging-
директории (`_staging/<batch_id>/...`) в целевые партиции через
`Path.replace()` — атомарно **в пределах одной сущности**, но не
между тремя сущностями сразу. Порядок и откат при сбое покрыты
тестами (`tests/test_generate_data.py::TestPublishBatchAtomicity`).

### Клиенты и заказы накапливаются между запусками

`customers` и `orders` — обе сущности переиспользуются между запусками
(`payments` тоже, но только через переиздание при рефанде — см. ниже).
Каждый новый батч заказов может ссылаться на клиента,
зарегистрированного в **любой** из прошлых загрузок (см.
`load_existing_customers`). Заказы, ещё не закрытые (не оплачены, не
отменены, не доставлены и т.д.), подхватываются из истории (см.
`load_existing_orders`) и **продвигаются** по state machine на один
шаг за прогон (`advance_open_orders`) — заказ **переиздаётся новой
строкой с тем же `order_id`** в CSV того батча, где с ним что-то
произошло, вместо изменения уже опубликованной строки.

Глубина скана истории заказов ограничена (`compute_lookback_days`) —
суммой всех дедлайнов/окон state machine. За этим горизонтом любой
заказ гарантированно уже в терминальном статусе, читать историю
глубже бессмысленно (та же логика, что и для ограничения роста
`load_existing_customers` ниже, просто с явной верхней границей вместо
неограниченного роста).

### DQ-инжекция

`--error-rate` задаёт долю строк с намеренно испорченными данными,
поровну распределённую между несколькими типами ошибок на сущность
(`orders.null_customer_id`, `orders.negative_amount`,
`payments.duplicate_payment_id_rows`, `customers.null_customer_id` и
т.д. — полный список см. в `commit.json` после запуска). DQ-инжекция
применяется только к **новым** строкам этого батча (новые заказы,
новые попытки оплаты, новые клиенты) — не к строкам, переизданным
`advance_open_orders()` при продвижении уже существующих заказов, во
избежание порчи уже опубликованной истории.

Фактическое число инжектированных ошибок каждого типа фиксируется в
манифесте — это позволяет DQ-тестам в даунстриме проверять не только
«данные проходят валидацию», но и «валидация действительно ловит
ровно ту ошибку, которую мы туда положили».

Если батч слишком мал, чтобы вместить хотя бы одну ошибку каждого
типа при заданном `--error-rate`, генератор явно предупреждает об
этом в логах и фиксирует пропущенные типы в
`commit.json -> skipped_quality_issue_types`, вместо того чтобы
молча ничего не инжектировать.

### Типы DQ-ошибок (`dq_reason`)

Слой quarantine размечает каждую забракованную строку значением
`dq_reason` — кодом причины (или несколькими, если строка нарушает
сразу несколько правил: они склеиваются через `" | "`, см.
`add_dq_reason` в `transform.py`). Это **не то же самое**, что
идентификаторы инжектированных ошибок из `--error-rate`
(`orders.null_customer_id` и т. п., см. выше) — те описывают, что было
испорчено на этапе генерации сырых данных, а `dq_reason` — что именно
поймала валидация в `transform.py`. Однозначного 1:1 соответствия
между ними нет: часть причин ниже возникает только как побочный
эффект (например, `CUSTOMER_NOT_FOUND` — не прямая инжекция, а
следствие того, что связанный клиент сам оказался в карантине).

Каждый код ниже отмечен стандартным измерением DQ, которое он
проверяет:
- **Completeness** (полнота) — обязательное поле пустое/NULL
- **Uniqueness** (уникальность) — недопустимый дубликат
- **Validity** (валидность) — значение вне допустимого домена/формата
- **Consistency** (согласованность) — противоречие между полями
  одной записи, либо между записями разных сущностей (включая
  ссылочную целостность и порядок событий во времени)

**`customers`:**
- `CUSTOMER_ID_EMPTY` (Completeness) — `customer_id` пустой или NULL
- `CUSTOMER_ID_DUPLICATE_IN_LOAD` (Uniqueness) — `customer_id`
  повторяется внутри одного батча
- `CUSTOMER_ID_DUPLICATE_IN_HISTORY` (Uniqueness) — `customer_id` уже
  встречался в ранее загруженных батчах
- `REGISTRATION_DATE_INVALID` (Validity) — `registration_date` не
  распарсился/NULL

**`orders`:**
- `ORDER_ID_EMPTY` (Completeness) — `order_id` пустой или NULL
- `ORDER_ID_DUPLICATE_IN_LOAD` (Uniqueness) — `order_id` повторяется
  внутри одного батча (легитимное переиздание заказа в разных
  батчах ошибкой не считается, см. «Клиенты и заказы накапливаются
  между запусками» выше)
- `CUSTOMER_ID_EMPTY` (Completeness) — у заказа не указан `customer_id`
- `CUSTOMER_NOT_FOUND` (Consistency) — `customer_id` указан, но такого
  клиента нет в clean-слое `customers`
- `CREATED_AT_INVALID` (Validity) — `created_at` не распарсился/NULL
- `ORDER_AMOUNT_INVALID` (Validity) — `amount_kopecks` NULL или ≤ 0
- `ORDER_STATUS_INVALID` (Validity) — `status` вне списка
  `VALID_ORDER_STATUSES`
- `CANCELLATION_REASON_INCONSISTENT` (Consistency) —
  `cancellation_reason` заполнен при статусе, отличном от
  `cancelled`/`refunded`, либо статус `cancelled`, а причина не
  заполнена
- `REFUND_TIMELINE_INVALID` (Consistency) — `refunded_at` раньше
  `cancelled_at` или `returned_at`

**`payments`:**
- `PAYMENT_ID_EMPTY` (Completeness) — `payment_id` пустой или NULL
- `PAYMENT_ID_DUPLICATE_IN_LOAD` (Uniqueness) — `payment_id`
  повторяется внутри одного батча
- `ORDER_ID_EMPTY` (Completeness) — у платежа не указан `order_id`
- `ORDER_NOT_FOUND` (Consistency) — `order_id` указан, но такого
  заказа нет в clean-слое `orders`
- `PAYMENT_DATE_INVALID` (Validity) — `payment_date` не
  распарсился/NULL
- `PAYMENT_AMOUNT_INVALID` (Validity) — `amount_kopecks` NULL или ≤ 0
- `PAYMENT_STATUS_INVALID` (Validity) — `status` вне списка
  `VALID_PAYMENT_STATUSES`
- `PAYMENT_BEFORE_ORDER` (Consistency) — `payment_date` раньше
  `created_at` связанного заказа

Заметь: измерение **Timeliness** (своевременность/свежесть данных) в
этом списке не представлено — задержка между событием и его
появлением в выгрузке существует и задокументирована («Батч —
календарный день, не час» в «Известные ограничения»), но не
размечается как `dq_reason`: пайплайн трактует её как ожидаемое
свойство батчевой модели, а не как DQ-нарушение.

Единственный источник истины — сами проверки в `add_dq_reason(...)`
внутри `transform_customers`/`transform_orders`/`transform_payments`
(`transform.py`); список выше синхронизирован с ними на момент
написания.

### Реалистичная динамика error_rate (`--launch-date`)

По умолчанию `--error-rate` — буквальный процент брака в каждом
батче, постоянный изо дня в день. Это не похоже на реальный DQ-дашборд:
там процент ошибок обычно выше сразу после запуска источника/интеграции
(баги ещё не отловлены) и снижается по мере взросления, поверх — день-в-
день шум и редкие инциденты у отдельных источников (сорвался
партнёрский API, деплой с багом и т.п.).

Флаг `--launch-date` включает эту динамику (`resolve_error_rate()` в
`generate_data.py`) поверх `--error-rate`, который в этом режиме
становится **базовым уровнем плато**, а не буквальным дневным
значением:

- **Ramp-up** (`_ramp_multiplier`) — в день запуска эффективный
  `error_rate` в `RAMP_ERROR_INITIAL_MULTIPLIER` (4×) выше базового,
  экспоненциально затухает к нему за `RAMP_ERROR_DECAY_DAYS` (21 день).
- **Шум** — логнормальный день-в-день джиттер (`ERROR_RATE_NOISE_SIGMA`)
  вокруг тренда, отдельно для каждой сущности.
- **Инциденты** (`_build_incident_calendar` / `_incident_multiplier`) —
  редкие 2–4-дневные всплески (×3–6) у случайной сущности. Календарь
  строится на фиксированном сиде, не зависящем от `--load-date`, поэтому
  каждый отдельный дневной запуск генератора детерминированно видит
  один и тот же календарь и корректно попадает в многодневные окна без
  persisted state между запусками.

Без `--launch-date` ничего из этого не действует — `error_rate`
передаётся как есть (обратная совместимость). Фактически применённое
значение по каждой сущности за день фиксируется в
`commit.json -> effective_error_rate` (наряду с буквальным
`configured_error_rate`). `backfill_history.sh` включает эту динамику,
передавая `--launch-date` равным дате открытия площадки.

### Реалистичный объём: шум и недельная сезонность

Кривая роста в `backfill_history.sh` (ramp-фаза + плато) сама по себе даёт
идеально гладкие числа — `customers_count`/`orders_count` растут по чистой
линейной формуле день в день, без разброса и без разницы между буднями и
выходными. На дашборде это выглядит неестественно ровно. Поверх неё
работают два независимых механизма:

- **Недельная сезонность** — `weekday_multipliers` в `growth_config.json`
  (ключи — ISO-номер дня недели, `1`=понедельник…`7`=воскресенье, тот же
  файл читает и `backfill_history.sh`, и Airflow DAG, чтобы коэффициенты не
  разъезжались между ручным бэкафиллом и ежедневным пайплайном).
  `backfill_history.sh` применяет multiplier к `customers_count`/
  `orders_count` **до** передачи их в `generate_data.py` — это
  детерминированный, повторяющийся из недели в неделю паттерн, а не
  случайность.
- **Шум** — `resolve_count()` в `generate_data.py`, мультипликативный
  логнормальный джиттер (`VOLUME_NOISE_SIGMA`) поверх уже
  сезонно-скорректированного объёма. Включается вместе с `--launch-date`,
  как и `resolve_error_rate()`; без него `--customers-count`/
  `--orders-count`/`--payments-count` передаются как есть (обратная
  совместимость). Применяется независимо к каждой из трёх сущностей —
  `customers_count` и `orders_count` шумят по отдельности (значит их
  соотношение день ото дня тоже слегка гуляет), `payments_count` шумит
  отдельно от них обоих. Фактически применённое значение по каждой
  сущности фиксируется в `commit.json -> effective_*_count` (наряду с
  буквальными `configured_*_count`).

`payments_count` при этом получает недельную сезонность только косвенно:
`backfill_history.sh` считает его как процент (`payments_margin_pct`) от
уже сезонно-скорректированного `orders_count`, но собственной строки в
`weekday_multipliers` у него нет. Из-за того, что шум `orders_count` и
шум `payments_count` — два независимых броска `resolve_count()`, их
соотношение в отдельные дни может отклониться от заданного
`payments_margin_pct` заметнее, чем задумывалось (например, оба шума
разом пойдут в разные стороны). Это не ломает данные — механика пула
заказов в `generate_payments()` просто не расходует лишний бюджет
попыток или переносит недостачу на следующий день, — но делает долю
`not_paid_in_time` чуть более волатильной день ото дня, что для
реалистичности скорее плюс, чем минус.

### Часовой профиль зависит от дня недели

`_realistic_timestamps()` в `generate_data.py` использует один из двух
наборов весов по часам суток — `WEEKDAY_HOUR_WEIGHTS` (будни, острый
вечерний пик 18–21ч после работы, провал в рабочие часы с обеденным
всплеском в 12ч) или `WEEKEND_HOUR_WEIGHTS` (выходные, более ровное
дневное плато 14–17ч без острого пика, поздний старт с утра) — в
зависимости от `date.weekday()` даты, для которой генерируется
временная метка. Затрагивает `created_at` заказов и `registration_date`
клиентов. Будни между собой используют один и тот же профиль (как и
выходные между собой) — см. оговорку в «Известных ограничениях» выше.

### Калибровка под универсальный маркетплейс (Ozon/Wildberries-стиль)

Проект не привязан к одной товарной вертикали, но числовые параметры
калиброваны под собирательный образ российского универсального
маркетплейса смешанных категорий (одежда, электроника, товары для
дома), а не под fashion-only или grocery-only бизнес — для другой
вертикали эти константы стоит пересчитать заново, а не считать
универсальными:

- **`generate_order_amounts()`** (`generate_data.py`) — логнормальное
  распределение суммы заказа, `mean=11.9, sigma=0.8`, клип
  [150₽, 150 000₽]. Даёт медиану ~1475₽, средний чек ~2000₽, с хвостом
  в сторону крупной бытовой техники/электроники — соответствует
  публичным ориентирам среднего чека Ozon/Wildberries, а не
  единственному товару.
- **`return_rate: 0.15`** (`growth_config.json`) — блендированная по
  всем категориям доля возвратов. Выше, чем у монокатегорийного
  магазина электроники (там счёт на единицы процентов), из-за культуры
  «примерочной» у ПВЗ, характерной для одежды на российских
  маркетплейсах.
- **`_customer_order_weights()`** (`generate_data.py`) — вес клиента
  при выборе, кому принадлежит новый заказ, детерминированный
  (из md5 `customer_id`, не из `rng` батча) и экспоненциально
  распределённый. Раньше каждый заказ доставался случайному клиенту
  равновероятно (`rng.integers`), из-за чего повторные покупки не
  концентрировались на лояльном ядре, а размазывались по всей базе
  ровным слоем. Стабильность веса во времени важна: один и тот же
  клиент остаётся активным/пассивным изо дня в день, а не
  перевыбирается заново на каждом батче.
- **`ACQUISITION_CHANNEL_LOYALTY_MULTIPLIER`** (`generate_data.py`) —
  домножает вес из `_customer_order_weights()` по каналу привлечения
  клиента (`customers.acquisition_channel`). Раньше канал был статичной
  меткой без последствий для дальнейшего поведения. Органика/рефералы/
  email (уже вовлечённая или доверяющая бренду аудитория) получают
  множитель 1.2–1.4, платный social (vk/telegram/social ads, типичный
  «один клик — один заказ») — 0.6–0.7, `yandex_direct`
  (performance-поиск с явным интентом) — 1.0. Соответствует типичному
  разрыву LTV по каналам в e-commerce.
- **`--never-order-rate`** (по умолчанию `0.18`) и
  **`ACQUISITION_CHANNEL_NON_CONVERSION_MULTIPLIER`**
  (`generate_data.py`) — доля зарегистрировавшихся, которые не сделают
  ни одного заказа никогда. Раньше вес клиента был строго положительным,
  поэтому при достаточном числе заказов заказ рано или поздно доставался
  каждому, и конверсия «регистрация → первый заказ» в данных была
  ровно 100% — метрика существовала, но ничего не измеряла.
  `_customer_never_orders()` помечает часть базы нулевым весом. Признак
  детерминирован из `customer_id` (как и вес частоты), поэтому ушедший
  клиент остаётся ушедшим и на следующих батчах, но берётся **другой
  срез md5** — иначе «не купит никогда» и «покупает редко» были бы одним
  признаком, и неконвертящиеся оказались бы просто хвостом
  распределения частоты. Доля зависит от канала: рефералы и органика
  дают 0.6–0.7 от базовой ставки, платный social — 1.4–1.6.
  На горизонте бэкафилла это даёт конверсию около 80–85% с разбросом по
  каналам от ~56% (`telegram_ads`) до ~82% (`referral`).

### Реалистичная динамика PAYMENT_SUCCESS_RATE (`--launch-date`)

По той же логике, что и `error_rate`: `PAYMENT_SUCCESS_RATE` (0.95) по
умолчанию — жёсткая константа, одинаковая каждый день, что на дашборде
«% успешных платежей» выглядит как идеально ровная линия с одним лишь
биномиальным шумом сэмплирования. `resolve_payment_success_rate()`
добавляет реальную динамику через `failure_rate = 1 - PAYMENT_SUCCESS_
RATE`, к которому применяется тот же ramp+noise+incident механизм, что
и в `resolve_error_rate` (переиспользует `_ramp_multiplier`/
`_incident_multiplier` напрямую, со своими константами
`RAMP_PAYMENT_FAILURE_INITIAL_MULTIPLIER`/`RAMP_PAYMENT_FAILURE_DECAY_
DAYS`/`PAYMENT_FAILURE_NOISE_SIGMA`), а инцидентный всплеск берёт из уже
существующего календаря сущности `"payments"` — один и тот же сбой
платёжной инфраструктуры правдоподобно бьёт и по DQ, и по конверсии
оплаты одновременно. Итоговый `failure_rate` конвертируется обратно в
`success_rate`. Без `--launch-date` ничего из этого не действует.
Фактическое значение за день — в `commit.json ->
effective_payment_success_rate` (наряду с буквальным
`configured_payment_success_rate`).

### Календарь дней особого объёма и нагрузка (`--launch-date`)

Помимо недельной сезонности (`weekday_multipliers`) объём заказов
зависит от типа календарного дня — праздник/зарплата/промо, см.
`resolve_calendar_day_type()`/`resolve_calendar_multiplier()` в
`generate_data.py`. В отличие от календаря инцидентов
(`_build_incident_calendar`) — это не случайные редкие сбои с
фиксированным сидом, а детерминированное правило по самой дате
(`месяц, день`), поэтому работает на любую дату сколь угодно далеко в
будущем без ручного сопровождения — важно, поскольку
`daily_marketplace_pipeline` (Airflow DAG) крутится ежедневно бессрочно,
а не только в пределах окна `backfill_history.sh`:

- **Праздник** (гос. нерабочие дни РФ, `HOLIDAY_VOLUME_MULTIPLIER=0.75`)
  — покупательская активность и логистика проседают.
- **Зарплата** (5-е/20-е число, `PAYDAY_VOLUME_MULTIPLIER=1.15`) — есть
  на что тратить.
- **Промо** (11.11, «чёрная пятница» — последняя пятница ноября,
  `PROMO_VOLUME_MULTIPLIER=2.5`) — то, ради чего люди ждут конкретный
  день.

При совпадении типов дня множители не перемножаются — приоритет
promo > holiday > payday (`resolve_calendar_day_type`), чтобы не
накручивать эффект сверх правдоподобного. Множитель применяется в
`resolve_count()` поверх дневного логнормального шума и до клипа снизу
в 1.

**Перенос выходных дней — приближённый, не сверен с фактическими
постановлениями Правительства РФ.** `_holiday_dates_for_year()`
реализует упрощённую эвристику: если праздник выпал на субботу/
воскресенье, нерабочим считается ближайший следующий будний день.
Реальные переносы бывают сложнее (переносят не всегда «на понедельник
сразу после», иногда — вообще другую дату года ради длинных мостов) и
публикуются отдельным постановлением на каждый год, что для этого
проекта означало бы таблицу дат, требующую ежегодного ручного
пополнения. Для синтетических тестовых данных сочтено, что бессрочная
работа эвристики важнее её буквальной точности.

**Нагрузка → конверсия оплаты и отмены.** `load_ratio` в `main()` —
отношение фактического (после шума и календаря) объёма заказов дня к
базовому. Когда `load_ratio > 1` (промо/зарплата, а иногда и просто
случайный шумовой всплеск — не обязательно календарный день),
`resolve_load_stress_multiplier()` пропорционально поднимает
`failure_rate` в `resolve_payment_success_rate()` и домножает
`cancel_before_payment_rate`/`cancel_after_payment_rate` перед
`advance_open_orders()` — платёжный шлюз и склад не резиновые. Работает
только "вверх": тихий день (`load_ratio <= 1`) не улучшает конверсию,
только перегруженный её ухудшает. Без `--launch-date` `load_ratio`
всегда равен 1.0 (обратная совместимость). Фактические значения за
день — в `commit.json -> load_ratio`/`calendar_day_type`/
`effective_cancel_*_payment_rate`.

### Географическое распределение клиентов (`CITY_WEIGHTS`)

`city` в `customers` берётся не равновероятно из списка городов-
миллионников (`CITIES`), а взвешенно — `CITY_WEIGHTS` в
`generate_data.py`, нормализуется и передаётся в `rng.choice(..., p=...)`
внутри `generate_customers()`. Веса грубо отражают реальную долю
e-commerce-спроса по городам: Москва и Санкт-Петербург непропорционально
доминируют (~30% и ~15% соответственно), остальные миллионники — длинный
хвост. Без весов равновероятный выбор давал визуально неправдоподобную
картину на дашбордах («Клиенты по городам» показывал Москву наравне с
Омском или Волгоградом).

### State machine заказа

```
new ──(не оплачен за payment-deadline-hours)───────────► cancelled [not_paid_in_time]
new ──(клиент передумал до оплаты)─────────────────────► cancelled [cancelled_by_customer_before_payment]
new ──(успешная оплата)──► paid ──(окно отправки)──► shipped ──(окно доставки)──► ready_for_pickup ──(окно на забор)──► delivered
paid/shipped/ready_for_pickup ──(отменил после оплаты)─► cancelled [cancelled_by_customer_after_payment] ──► refunded
ready_for_pickup ──(не забрал за pickup-deadline-days)─► cancelled [not_picked_up_in_time] ──► refunded
delivered ──(вернул товар)──────────────────────────────► returned ──► refunded
```

Это полноценная событийная state machine, а не одноразовый случайный
розыгрыш финального статуса: заказ создаётся один раз со `status=new`
и дальше продвигается по реальным правилам (`advance_open_orders`),
переиздаваясь новой строкой при каждом изменении состояния.
`refunded` — не отдельная параллельная ветка, а финансовое разрешение,
наступающее **после** `cancelled` или `returned`, и только если была
успешная оплата (иначе возвращать нечего, `cancelled` терминален).
`cancellation_reason` заполняется в момент первого перехода в
`cancelled` и остаётся заполненным даже после `refunded` — а для
заказов, прошедших `delivered → returned → refunded`, остаётся `NULL`
на всём пути (эта ветка `cancelled` вообще не касается).

Читать историю переходов заказа построчно (кто в какой момент был
`shipped`, потом `ready_for_pickup` и т.д.) из `orders` напрямую
нельзя — `ReplacingMergeTree` физически удаляет старые версии строки
при фоновом мердже, это не event-лог. Но полный **таймлайн вех**
восстановим всегда: каждое переиздание переносит уже достигнутые
milestone-поля (`paid_at`, `shipped_at`, `ready_for_pickup_at`,
`delivered_at`, `cancelled_at`, `returned_at`, `refunded_at`) вперёд —
на актуальной (после `FINAL`) строке видны все пройденные вехи разом.

### Запросы к ClickHouse: FINAL обязателен

Между вставкой переизданной строки и фоновым мерджем `ReplacingMergeTree`
в таблице какое-то время физически лежат **обе** версии заказа —
старая и новая. Наивный `SELECT ... FROM orders GROUP BY status`
в этом окне задвоит заказ сразу в двух статусах. Правильно:

```sql
SELECT status, count() FROM orders FINAL GROUP BY status
```

`FINAL` заставляет ClickHouse разрешить дубликаты по ключу
(`created_at`, `customer_id`, `order_id`) в момент запроса, а не ждать
фонового мерджа. Альтернатива — `argMax(status, ingested_at)` с
группировкой по `order_id`, если `FINAL` неприемлем по перформансу.

### Семантический слой (`clickhouse_marts.sql`)

Витрины дашборда — объекты ClickHouse в отдельной базе
`marketplace_marts`, а не SQL внутри Superset. Раньше определения GMV,
«зрелости» заказа, воронки и словари статусов существовали
единственным экземпляром в `form_data` чартов: их нельзя было
переиспользовать вне дашборда, проверить запросом или посмотреть в
истории отдельно от раскладки.

Два уровня:

- **Уровень 1** — `customers` / `orders` / `payments`: дедупликация
  (`FINAL`) и словари enum'ов в человеческие подписи. Единственное
  место, где произносится `FINAL`.
- **Уровень 2** — `order_funnel_stages`, `orders_with_customer_dim`,
  `customer_first_order`, `first_order_delay_distribution`,
  `refund_processing_times`, `dq_reason_breakdown`,
  `quarantine_volume`, `load_freshness`. Строятся поверх уровня 1,
  поэтому `FINAL` и словари в них не повторяются.

Отдельная база, а не префикс: сырой и семантический слои разделены
физически, и витрина может называться `orders`, не конфликтуя с
`marketplace_analytics.orders`. Благодаря этому имена витрин совпадают
с именами датасетов Superset один в один — перевод датасета на витрину
не требует переименования, и чарты, ссылающиеся на датасет по id,
ничего не замечают.

Это `VIEW`, а не `MATERIALIZED VIEW`: на объёмах MVP всё считается на
лету, а материализация означала бы ещё один слой, который нужно
обновлять и инвалидировать. Пересматривать при росте данных.

Горизонты зрелости (`{{MATURITY_DAYS}}`, `{{CUSTOMER_MATURITY_DAYS}}`)
подставляются при применении из `growth_config.json` — того же файла,
что читают генератор, бэкафилл и Airflow DAG. Захардкодить их в SQL
значило бы завести хранилищу собственную копию бизнес-правил.

Применяется автоматически: `load_to_clickhouse.py` (`ensure_marts`)
переналивает витрины при любой загрузке, включая no-op на уже
загруженный день, — изменившееся правило доезжает до дашборда без
отдельного шага. Витрины вычисляются на лету, поэтому пересоздавать их
каждый раз ничего не стоит.

Согласованность списка витрин со списком датасетов в
`superset/apply_review_fixes.py` закреплена тестами
(`tests/test_marts.py`): типовая поломка семантического слоя — витрину
переименовали, а BI остался смотреть на старое имя.

### Идемпотентная загрузка в ClickHouse

Схема таблиц закоммичена в `clickhouse_schema.sql` (единственный
источник истины — раньше таблицы существовали только в живом
кластере). `load_to_clickhouse.py` применяет её (`CREATE ... IF NOT
EXISTS`) при каждом запуске, поэтому отдельного шага миграции не
требуется.

`write_clickhouse()` делает голый `.append()` — сам по себе он не
защищён от повторной загрузки одного и того же `load_date` (например,
при повторном запуске после сбоя коннектора). Идемпотентность
обеспечивается снаружи, тем же принципом, что commit-маркер в
`generate_data.py`:

- перед загрузкой `load_to_clickhouse.py` проверяет таблицу
  `_load_commits` — если `load_date` там уже есть, скрипт ничего не
  грузит и завершается (no-op), не поднимая даже `SparkSession`;
- `--force-reload` перезаписывает день: сначала `ALTER TABLE ... DROP
  PARTITION` по всем таблицам, партиционированным по `load_date`
  (метаданная операция, не мутация — быстро, без write amplification),
  потом обычная загрузка;
- запись в `_load_commits` — последний шаг, после того как все
  сущности успешно догружены. Если скрипт упадёт раньше — маркер не
  запишется, и следующий запуск честно догрузит день заново.

### Ежедневный пайплайн в Airflow (`dags/daily_marketplace_pipeline.py`)

`backfill_history.sh` + `run_downstream_pipeline.sh` — для ручного
бэкафилла истории. `dags/daily_marketplace_pipeline.py` — тот же набор
шагов (`generate_data.py` -> `ingest_csv_to_raw.py` -> `transform.py` ->
`load_to_clickhouse.py`), но на регулярном расписании (`@daily`), один
день (logical_date) за раз, для продакшен-режима.

Бизнес-параметры и объём читаются из того же `growth_config.json`, что
и `backfill_history.sh` — коэффициенты и кривая роста не расходятся
между ручным бэкафиллом и ежедневным пайплайном (см. «Реалистичный
объём» выше). Подключение к ClickHouse — из `clickhouse_config.json`;
пароль в DAG'е не хранится нигде в репозитории — берётся из Airflow
Connection `clickhouse_default` (её нужно завести в Admin -> Connections
перед первым запуском).

`max_active_runs=1`: дни должны идти строго по порядку — `generate_data.py`
накапливает клиентов между запусками, а `transform.py` проверяет дубли
`customer_id` относительно уже обработанной истории (см. «Клиенты и
заказы накапливаются между запусками» выше и комментарий в
`run_downstream_pipeline.sh`). Это ограничение, не деталь реализации —
не увеличивать `max_active_runs` и не запускать дни параллельно.

Зависимости DAG'а — отдельно, `requirements-airflow.txt` (Airflow —
тяжёлая зависимость, не нужна ни генератору, ни Spark-скриптам сама по
себе). Сами `generate_data.py`/`ingest_csv_to_raw.py`/`transform.py`/
`load_to_clickhouse.py` DAG вызывает как внешние процессы
(`subprocess.run`), а не импортирует — воркеру Airflow всё равно
нужны их зависимости (`requirements-spark.txt` в т.ч.) в PATH.

## Универсальность архитектуры

Разделение по слоям, что здесь переиспользуемо для любого домена, а
что специфично именно для маркетплейса:

**Domain-agnostic (архитектура пайплайна):**
- Hive-style партиционирование и commit-контракт (см. выше) —
  работает для любых сущностей, не только customers/orders/payments.
- DQ-framework в `transform.py` (`add_dq_reason`/`split_valid_invalid`,
  паттерн quarantine-слоя) — набор проверок передаётся списком, не
  привязан к конкретным полям.
- Upsert-паттерн переиздания строк по ключу (заказ/платёж переиздаётся
  новой строкой при изменении состояния, `ReplacingMergeTree` разрешает
  версии по `ingested_at`) — годится для любой сущности с изменяемым
  состоянием: банковского счёта, заявки на кредит, брони отеля.

**Domain-specific (эта конкретная реализация):**
- Схема `generate_data.py` целиком: статусы, дедлайны, причины отмены,
  ready_for_pickup — это глубоко проработанный, но именно
  маркетплейс-специфичный пример поверх универсального движка, а не
  единственно возможный. Для другого домена (банк, сетевая розница)
  схема и state machine писались бы заново, а слой выше — переиспользуется
  как есть.

## Известные ограничения

### Часть зрелых заказов остаётся в открытом статусе

Около 4% заказов старше горизонта закрытия (34 дня) лежат в хранилище
как «новый», «оплачен», «отправлен», «готов к выдаче» или «возвращён» —
хотя по сумме дедлайнов такого быть не должно.

Это не дыра в state machine, а видимое следствие DQ-инжекции.
Генератор эти заказы закрывает, но закрывающая строка несёт внедрённый
дефект (`CANCELLATION_REASON_INCONSISTENT` или
`REFUND_TIMELINE_INVALID`), `transform.py` отбраковывает её в карантин,
и в ClickHouse остаётся последняя валидная версия — открытая.

Проверено: **все** такие заказы имеют строку в `quarantine_orders`.
Ровно это и утверждает проверка «SLA: незакрытые зрелые заказы
объяснены карантином» в `marts_checks.py` — незакрытый заказ без строки
в карантине означал бы уже настоящую ошибку продвижения статусов.

Побочный вывод, который стоит держать в голове при чтении дашборда:
доли статусов считаются по тому, что доехало до хранилища, а не по
тому, что произошло в источнике. Брак смещает их в сторону открытых
состояний.

### Дубликаты ID ищутся в окне, а не во всей истории

`read_historical_keys()` в `transform.py` отбирает ID из clean-слоя за
последние 365 дней (`DUPLICATE_LOOKBACK_DAYS`), а не за всю историю.

Прежняя версия фильтровала партиции условием «дата не равна текущей» —
под такое Spark не умеет отсекать партиции и читал весь слой целиком на
каждой ночной загрузке. На пятидесяти днях это незаметно, на трёх годах
каждая ночь дороже предыдущей.

Цена: повторно выданный `customer_id`, чей оригинал старше года,
проверкой `CUSTOMER_ID_DUPLICATE_IN_HISTORY` не поймается. В самом
хранилище такие строки всё равно схлопнет `ReplacingMergeTree` по ключу
— потерять данные это не может, но метрика качества их не увидит.

### Прочее

Осознанно не реализовано в этой версии — для MVP было решено, что
это не окупает сложность прямо сейчас:

- **Нет товарного измерения** (order items, SKU, категории) —
  нельзя тестировать ABC-анализ, cross-sell, category mix.
- **Нет сезонности/трендов у `generate_data.py` как таковой** — сама по
  себе она не знает о дне недели или месяце; сезонность объёма
  (`weekday_multipliers`) и профиль будни/выходные
  (`WEEKDAY_HOUR_WEIGHTS`/`WEEKEND_HOUR_WEIGHTS`, см. «Часовой профиль
  зависит от дня недели» выше) — это надстройка `backfill_history.sh` +
  сам генератор соответственно, а не свойство ядра. Будни между собой
  (пн–пт) и выходные между собой (сб/вс) по-прежнему используют один и
  тот же почасовой профиль каждый — различаются только эти две группы,
  не все семь дней по отдельности. **Важный побочный эффект при
  агрегации по дню недели:** если диапазон дат генерации не кратен 7
  дням, некоторые дни недели попадут в выборку на один раз больше
  других (например, 12 понедельников против 11 суббот) — и сумма/`COUNT`
  по дню недели усилит и так уже реальный недельный паттерн
  неконтролируемым образом. При построении дашбордов/чартов,
  агрегирующих что-либо по дню недели, использовать `AVG` (или
  `COUNT(*) / COUNT(DISTINCT дата)`), а не голый `SUM`/`COUNT` — иначе
  разное число дат на каждый день недели искажает картину сверх
  заданных `weekday_multipliers`.
- **Клиенты иммутабельны** — нет SCD2 (смена города, канала и
  т.п.), нет дублей клиентов (одна персона — два `customer_id`).
- **Задержек доставки нет** — время в пути всегда строго меньше
  `--delivery-deadline-days`/`--pickup-deadline-days`. Можно добавить
  отдельным шагом позже.
- **Батч — календарный день, не час.** Короткий (например, часовой)
  `--payment-deadline-hours` создаёт заметную задержку между реальным
  моментом события (клиент не оплатил) и его появлением в выгрузке
  (только на следующий день) — timestamps при этом остаются точными,
  страдает только свежесть данных, не их корректность. Переход на
  батчи чаще раза в день — самостоятельная архитектурная задача
  (другой commit-контракт, другая партиционная схема), не покрыта
  этой версией.
- **Seed зависит только от `--load-date`**, не от остальных
  параметров запуска — прогон одной и той же даты с другим
  `--customers-count` даёт другую случайность, но повторный прогон с
  идентичными параметрами полностью детерминирован.
- **`load_existing_customers` перечитывает всех исторических
  клиентов при каждом запуске** — с ростом истории (сотни
  `load_date`) время старта будет расти линейно. Для объёма MVP
  это не проблема; при росте истории потребует индекса/кэша.
  `load_existing_orders`, в отличие от клиентов, эту проблему уже не
  имеет — глубина скана там ограничена явно.
- **Доля отмен/возвратов искусственно падает в последние ~34 дня
  выгрузки (right-censoring).** `advance_open_orders` — событийная
  state machine: заказ продвигается к `cancelled`/`returned`/
  `refunded` только за счёт последующих ежедневных запусков
  генератора, «будущего» после последнего `load_date` не существует.
  `compute_lookback_days()` суммирует все дедлайны состояний
  (оплата, отправка, доставка, забор, окно возврата, обработка
  рефанда) и даёт ≈34 дня — горизонт, после которого судьба заказа
  гарантированно определена. Заказы, созданные позже этого горизонта
  до последнего `load_date`, ещё не успели «дозреть» до отмены или
  возврата и висят в промежуточных статусах — при агрегации доли
  отмен/возвратов по дате создания заказа это выглядит как
  снижающийся тренд к концу периода, хотя реальная склонность к
  отменам не изменилась. При построении такой метрики — либо
  отбрасывать последние ~34 дня перед `max(load_date)`, либо считать
  на фиксированном окне созревания (% заказов, отменённых/возвращённых
  в течение N дней с момента создания), а не «на сегодня».

## Тестирование

```bash
pip install -r requirements-dev.txt
pytest -v
```

Два набора, разделённые по весу зависимостей.

**Генератор** (`tests/test_generate_data.py`) — граничные случаи
`error_count`, откат `publish_batch` при сбое посреди публикации, state
machine заказа (`advance_open_orders`, дедлайны, причины отмены),
валидация аргументов CLI.

**DQ-правила** (`tests/test_transform_dq.py`) — каждая проверка
`transform.py` в изоляции: берётся заведомо валидная строка, меняется
ровно одно поле, проверяется состав `dq_reason`. Правила вынесены из
`transform_*` в `customer_dq_checks()` / `order_dq_checks()` /
`payment_dq_checks()` именно для этого — они не трогают ни файлы, ни
партиции, поэтому проверяются на однострочном DataFrame без всякой
инфраструктуры.

Второй набор требует `pyspark` и JVM; без них файл пропускается
(`pytest.importorskip`), чтобы прогон тестов генератора не тянул
тяжёлую зависимость:

```bash
pip install -r requirements-spark.txt
pytest tests/test_transform_dq.py -v
```

В CI это отдельный job (`dq-rules`) с установкой Java 17.

## Требования к окружению

Python 3.10+ и, для Spark-слоя, JVM 17.

Зависимости описаны в двух формах. `requirements*.txt` — входные
файлы с широкими диапазонами, их правят руками:

| Файл | Для чего |
| --- | --- |
| `requirements.txt` | Генератор и ingest |
| `requirements-dev.txt` | То же + `pytest`/`ruff` |
| `requirements-spark.txt` | То же + `pyspark` для `transform.py` и `load_to_clickhouse.py` |
| `requirements-airflow.txt` | То же + `apache-airflow` для DAG'а |

`requirements*.lock` — результат их компиляции: точные версии всего
дерева зависимостей вместе с хешами. Их не редактируют руками, их
пересобирают:

```bash
pip install pip-tools
pip-compile --generate-hashes --strip-extras --output-file=requirements.lock requirements.txt
pip-compile --generate-hashes --strip-extras --output-file=requirements-dev.lock requirements-dev.txt
pip-compile --generate-hashes --strip-extras --output-file=requirements-spark.lock requirements-dev.txt requirements-spark.txt
```

Ставятся они с `--require-hashes`, и так это делает CI:

```bash
pip install --require-hashes -r requirements-dev.lock
```

Смысл разделения: разработчик читает и правит `.txt`, а CI и прод
ставят `.lock` и получают ровно тот же набор версий, что и вчера, —
иначе свежий релиз транзитивной зависимости роняет сборку без единого
коммита в репозиторий.

Airflow намеренно оставлен без lock-файла: его дерево зависимостей
огромно, жёстко завязано на версию Python и на констрейнты самого
Airflow, и разрешается на стороне той установки, куда DAG кладётся, —
пиннинг здесь дал бы ложную воспроизводимость, а не настоящую.
