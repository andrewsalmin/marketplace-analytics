# Synthetic Marketplace Data Generator

Генератор синтетических данных для MVP аналитической платформы —
конкретно **маркетплейса с логистикой доставки через пункты выдачи**
(модель в духе Ozon/Wildberries), не универсального e-commerce и не
сетевой розницы. У сетевой розницы (Пятёрочка, Магнит) транзакция
принципиально проще — покупка в моменте, без цепочки
shipped→ready_for_pickup→delivered — это не частный случай данной
модели, а другая модель, требующая своей state machine. Генератор
имитирует ежедневную выгрузку `clients` / `orders` / `payments` из
учётной системы (АС) в виде CSV-партиций, с контролируемой инжекцией
DQ-ошибок для тестирования пайплайнов и дашбордов качества данных.

CSV — осознанный выбор, а не недосмотр: генератор имитирует именно
**сырую выгрузку из источника**. Преобразование в Parquet — зона
ответственности отдельного downstream-скрипта, не этого репозитория.

## Быстрый старт

```bash
pip install -r requirements.txt

python generate_data.py \
  --load-date 2026-08-18 \
  --data-dir ./data \
  --clients-count 100 \
  --orders-count 15000 \
  --payments-count 15150 \
  --error-rate 0.01 \
  --payment-deadline-hours 24 \
  --shipping-deadline-hours 48 \
  --delivery-deadline-days 7 \
  --pickup-deadline-days 7 \
  --return-window-days 14 \
  --refund-processing-hours 72 \
  --cancel-before-payment-rate 0.02 \
  --cancel-after-payment-rate 0.01 \
  --return-rate 0.05
```

Все параметры дедлайнов/вероятностей опциональны — значения выше
одновременно являются дефолтами, если их не указывать явно.

Повторный запуск с тем же `--load-date` для того же `--data-dir`
намеренно завершится ошибкой — см. «Контракт партиционирования» ниже.

Чтобы увидеть реальную state machine в действии, запусти генератор
несколько раз подряд с последовательными датами (`--load-date`) —
заказы, не закрытые в один прогон (не оплаченные, не отправленные и
т.д.), будут подхватываться и продвигаться в следующих.

## Полный прогон: от генерации до ClickHouse

Разовый запуск `generate_data.py` выше — только для знакомства с
генератором. Чтобы прогнать весь пайплайн (source → raw →
clean/quarantine → ClickHouse) на реалистичной истории (рампа + плато,
см. `backfill_month.sh`), нужны все слои по очереди.

**1. Зависимости**

```bash
pip install -r requirements.txt
pip install -r requirements-spark.txt   # для transform.py и load_to_clickhouse.py
```

**2. Поднять ClickHouse**

Схема (`clickhouse_schema.sql`) применяется автоматически при первом
же запуске `load_to_clickhouse.py` (`ensure_schema()`) — руками её
создавать не нужно, нужен только сам сервер:

```bash
export CLICKHOUSE_PASSWORD=<придумай-пароль>
docker compose up -d clickhouse
```

Поднимает `clickhouse/clickhouse-server` с пользователем
`analytics_user`/`$CLICKHOUSE_PASSWORD` и базой `analytics` (HTTP —
`localhost:8123`, native-протокол для `clickhouse-client` —
`localhost:9000`). См. `docker-compose.yml`.

**3. Сгенерировать историю (source-слой)**

```bash
./backfill_month.sh
```

92 дня (2026-06-01 → 2026-08-31, весь летний сезон), рампа объёма 27 дней + плато. Форма
кривой и диапазон дат — константы в начале скрипта, меняются на месте.
При сбое посреди прогона — `./backfill_month.sh <день>` (см.
комментарий в шапке скрипта).

Помимо объёма, скрипт передаёт `--launch-date`, включающую отдельную
(более быструю, 21 день) динамику `error_rate` — см. «Реалистичная
динамика error_rate» ниже.

**4. Прогнать вниз по пайплайну (raw → clean/quarantine → ClickHouse)**

```bash
./run_downstream_pipeline.sh "$CLICKHOUSE_PASSWORD"
```

Для каждого дня: `ingest_csv_to_raw.py` → `transform.py` →
`load_to_clickhouse.py`. Загрузка в ClickHouse идемпотентна (см.
«Идемпотентная загрузка в ClickHouse» ниже) — скрипт безопасно
перезапускать, уже загруженные дни просто пропускаются.

И `backfill_month.sh`, и `run_downstream_pipeline.sh` могут идти часами
(генерация + Spark на десятки дней). Обычный foreground-процесс в
SSH-сессии получит `SIGHUP` и оборвётся при закрытии терминала —
запускай в чём-то, что переживает отключение:

```bash
# tmux/screen — можно вернуться и посмотреть прогресс
tmux new -s pipeline
./run_downstream_pipeline.sh "$CLICKHOUSE_PASSWORD"
# отключиться: Ctrl+B, затем D; вернуться: tmux attach -t pipeline

# либо nohup + фон
nohup ./run_downstream_pipeline.sh "$CLICKHOUSE_PASSWORD" > pipeline.log 2>&1 &
disown
# прогресс: tail -f pipeline.log
```

**Перезагрузить один конкретный день** (например, если подозреваешь
задвоение из-за более раннего сбоя коннектора):

```bash
python load_to_clickhouse.py \
  --load-date 2026-07-28 \
  --clickhouse-password "$CLICKHOUSE_PASSWORD" \
  --force-reload
```

**Проверить, что реально загружено:**

```bash
docker exec -it analytics-clickhouse clickhouse-client \
  --user analytics_user --password "$CLICKHOUSE_PASSWORD" \
  --query "SELECT load_date, entity, rows, loaded_at FROM analytics._load_commits ORDER BY load_date"
```

## Архитектура

### Партиционирование и layout на диске

```
data/source/
  clients/load_date=YYYY-MM-DD/clients.csv
  orders/load_date=YYYY-MM-DD/orders.csv
  payments/load_date=YYYY-MM-DD/payments.csv
  _commits/load_date=YYYY-MM-DD/commit.json
```

Каждый запуск генератора — это один батч, привязанный к одной дате
загрузки (`--load-date`). Внутри батча три сущности пишутся в
отдельные Hive-style партиции.

### Контракт для потребителей данных

**Партиция считается доступной для чтения только тогда, когда для
неё существует `_commits/load_date=.../commit.json`.** Если
commit-маркера нет — партиция не готова (или публикация упала
посередине), читать её нельзя, даже если файлы `clients.csv` /
`orders.csv` / `payments.csv` физически на месте.

Это осознанный выбор вместо истинной POSIX-атомарности между
несколькими директориями (которой на файловой системе просто не
существует): вместо неё используется commit-маркер как единственный
источник истины о готовности батча.

`publish_batch()` гарантирует, что для `source_root` в любой момент
времени верно ровно одно из двух:
- все три сущности **и** commit-маркер присутствуют, **или**
- ни одной из них там нет (если что-то упало посередине —
  уже перемещённое откатывается обратно в staging, а не остаётся
  «осиротевшим» без маркера).

`clients`/`orders`/`payments` перемещаются из временной staging-
директории (`_staging/<batch_id>/...`) в целевые партиции через
`Path.replace()` — атомарно **в пределах одной сущности**, но не
между тремя сущностями сразу. Порядок и откат при сбое покрыты
тестами (`tests/test_generate_data.py::TestPublishBatchAtomicity`).

### Клиенты и заказы накапливаются между запусками

`clients` и `orders` — обе сущности переиспользуются между запусками
(`payments` тоже, но только через переиздание при рефанде — см. ниже).
Каждый новый батч заказов может ссылаться на клиента,
зарегистрированного в **любой** из прошлых загрузок (см.
`load_existing_clients`). Заказы, ещё не закрытые (не оплачены, не
отменены, не доставлены и т.д.), подхватываются из истории (см.
`load_existing_orders`) и **продвигаются** по state machine на один
шаг за прогон (`advance_open_orders`) — заказ **переиздаётся новой
строкой с тем же `order_id`** в CSV того батча, где с ним что-то
произошло, вместо изменения уже опубликованной строки.

Глубина скана истории заказов ограничена (`compute_lookback_days`) —
суммой всех дедлайнов/окон state machine. За этим горизонтом любой
заказ гарантированно уже в терминальном статусе, читать историю
глубже бессмысленно (та же логика, что и для ограничения роста
`load_existing_clients` ниже, просто с явной верхней границей вместо
неограниченного роста).

### DQ-инжекция

`--error-rate` задаёт долю строк с намеренно испорченными данными,
поровну распределённую между несколькими типами ошибок на сущность
(`orders.null_client_id`, `orders.negative_amount`,
`payments.duplicate_payment_id_rows`, `clients.null_client_id` и
т.д. — полный список см. в `commit.json` после запуска). DQ-инжекция
применяется только к **новым** строкам этого батча (новые заказы,
новые попытки оплаты, новые клиенты) — не к строкам, переизданным
`advance_open_orders()` при продвижении уже существующих заказов, во
избежание порчи уже опубликованной истории.

Фактическое число инжектированных ошибок каждого типа фиксируется в
манифесте — это позволяет DQ-тестам в даунстриме проверять не только
«данные проходят валидацию», но и «валидация действительно ловит
ровно ту ошибку, которую мы туда положили».

Если батч слишком мал, чтобы вместить хотя бы одну ошибку каждого
типа при заданном `--error-rate`, генератор явно предупреждает об
этом в логах и фиксирует пропущенные типы в
`commit.json -> skipped_quality_issue_types`, вместо того чтобы
молча ничего не инжектировать.

### Типы DQ-ошибок (`dq_reason`)

Слой quarantine размечает каждую забракованную строку значением
`dq_reason` — кодом причины (или несколькими, если строка нарушает
сразу несколько правил: они склеиваются через `" | "`, см.
`add_dq_reason` в `transform.py`). Это **не то же самое**, что
идентификаторы инжектированных ошибок из `--error-rate`
(`orders.null_client_id` и т. п., см. выше) — те описывают, что было
испорчено на этапе генерации сырых данных, а `dq_reason` — что именно
поймала валидация в `transform.py`. Однозначного 1:1 соответствия
между ними нет: часть причин ниже возникает только как побочный
эффект (например, `CLIENT_NOT_FOUND` — не прямая инжекция, а
следствие того, что связанный клиент сам оказался в карантине).

Каждый код ниже отмечен стандартным измерением DQ, которое он
проверяет:
- **Completeness** (полнота) — обязательное поле пустое/NULL
- **Uniqueness** (уникальность) — недопустимый дубликат
- **Validity** (валидность) — значение вне допустимого домена/формата
- **Consistency** (согласованность) — противоречие между полями
  одной записи, либо между записями разных сущностей (включая
  ссылочную целостность и порядок событий во времени)

**`clients`:**
- `CLIENT_ID_EMPTY` (Completeness) — `client_id` пустой или NULL
- `CLIENT_ID_DUPLICATE_IN_LOAD` (Uniqueness) — `client_id`
  повторяется внутри одного батча
- `CLIENT_ID_DUPLICATE_IN_HISTORY` (Uniqueness) — `client_id` уже
  встречался в ранее загруженных батчах
- `REGISTRATION_DATE_INVALID` (Validity) — `registration_date` не
  распарсился/NULL

**`orders`:**
- `ORDER_ID_EMPTY` (Completeness) — `order_id` пустой или NULL
- `ORDER_ID_DUPLICATE_IN_LOAD` (Uniqueness) — `order_id` повторяется
  внутри одного батча (легитимное переиздание заказа в разных
  батчах ошибкой не считается, см. «Клиенты и заказы накапливаются
  между запусками» выше)
- `CLIENT_ID_EMPTY` (Completeness) — у заказа не указан `client_id`
- `CLIENT_NOT_FOUND` (Consistency) — `client_id` указан, но такого
  клиента нет в clean-слое `clients`
- `CREATED_AT_INVALID` (Validity) — `created_at` не распарсился/NULL
- `ORDER_AMOUNT_INVALID` (Validity) — `amount_kopecks` NULL или ≤ 0
- `ORDER_STATUS_INVALID` (Validity) — `status` вне списка
  `VALID_ORDER_STATUSES`
- `CANCELLATION_REASON_INCONSISTENT` (Consistency) —
  `cancellation_reason` заполнен при статусе, отличном от
  `cancelled`/`refunded`, либо статус `cancelled`, а причина не
  заполнена
- `REFUND_TIMELINE_INVALID` (Consistency) — `refunded_at` раньше
  `cancelled_at` или `returned_at`

**`payments`:**
- `PAYMENT_ID_EMPTY` (Completeness) — `payment_id` пустой или NULL
- `PAYMENT_ID_DUPLICATE_IN_LOAD` (Uniqueness) — `payment_id`
  повторяется внутри одного батча
- `ORDER_ID_EMPTY` (Completeness) — у платежа не указан `order_id`
- `ORDER_NOT_FOUND` (Consistency) — `order_id` указан, но такого
  заказа нет в clean-слое `orders`
- `PAYMENT_DATE_INVALID` (Validity) — `payment_date` не
  распарсился/NULL
- `PAYMENT_AMOUNT_INVALID` (Validity) — `amount_kopecks` NULL или ≤ 0
- `PAYMENT_STATUS_INVALID` (Validity) — `status` вне списка
  `VALID_PAYMENT_STATUSES`
- `PAYMENT_BEFORE_ORDER` (Consistency) — `payment_date` раньше
  `created_at` связанного заказа

Заметь: измерение **Timeliness** (своевременность/свежесть данных) в
этом списке не представлено — задержка между событием и его
появлением в выгрузке существует и задокументирована («Батч —
календарный день, не час» в «Известные ограничения»), но не
размечается как `dq_reason`: пайплайн трактует её как ожидаемое
свойство батчевой модели, а не как DQ-нарушение.

Единственный источник истины — сами проверки в `add_dq_reason(...)`
внутри `transform_clients`/`transform_orders`/`transform_payments`
(`transform.py`); список выше синхронизирован с ними на момент
написания.

### Реалистичная динамика error_rate (`--launch-date`)

По умолчанию `--error-rate` — буквальный процент брака в каждом
батче, постоянный изо дня в день. Это не похоже на реальный DQ-дашборд:
там процент ошибок обычно выше сразу после запуска источника/интеграции
(баги ещё не отловлены) и снижается по мере взросления, поверх — день-в-
день шум и редкие инциденты у отдельных источников (сорвался
партнёрский API, деплой с багом и т.п.).

Флаг `--launch-date` включает эту динамику (`resolve_error_rate()` в
`generate_data.py`) поверх `--error-rate`, который в этом режиме
становится **базовым уровнем плато**, а не буквальным дневным
значением:

- **Ramp-up** (`_ramp_multiplier`) — в день запуска эффективный
  `error_rate` в `RAMP_ERROR_INITIAL_MULTIPLIER` (4×) выше базового,
  экспоненциально затухает к нему за `RAMP_ERROR_DECAY_DAYS` (21 день).
- **Шум** — логнормальный день-в-день джиттер (`ERROR_RATE_NOISE_SIGMA`)
  вокруг тренда, отдельно для каждой сущности.
- **Инциденты** (`_build_incident_calendar` / `_incident_multiplier`) —
  редкие 2–4-дневные всплески (×3–6) у случайной сущности. Календарь
  строится на фиксированном сиде, не зависящем от `--load-date`, поэтому
  каждый отдельный дневной запуск генератора детерминированно видит
  один и тот же календарь и корректно попадает в многодневные окна без
  persisted state между запусками.

Без `--launch-date` ничего из этого не действует — `error_rate`
передаётся как есть (обратная совместимость). Фактически применённое
значение по каждой сущности за день фиксируется в
`commit.json -> effective_error_rate` (наряду с буквальным
`configured_error_rate`). `backfill_month.sh` включает эту динамику,
передавая `--launch-date` равным дате открытия площадки.

### Географическое распределение клиентов (`CITY_WEIGHTS`)

`city` в `clients` берётся не равновероятно из списка городов-
миллионников (`CITIES`), а взвешенно — `CITY_WEIGHTS` в
`generate_data.py`, нормализуется и передаётся в `rng.choice(..., p=...)`
внутри `generate_clients()`. Веса грубо отражают реальную долю
e-commerce-спроса по городам: Москва и Санкт-Петербург непропорционально
доминируют (~30% и ~15% соответственно), остальные миллионники — длинный
хвост. Без весов равновероятный выбор давал визуально неправдоподобную
картину на дашбордах («Клиенты по городам» показывал Москву наравне с
Омском или Волгоградом).

### State machine заказа

```
new ──(не оплачен за payment-deadline-hours)───────────► cancelled [not_paid_in_time]
new ──(клиент передумал до оплаты)─────────────────────► cancelled [cancelled_by_customer_before_payment]
new ──(успешная оплата)──► paid ──(окно отправки)──► shipped ──(окно доставки)──► ready_for_pickup ──(окно на забор)──► delivered
paid/shipped/ready_for_pickup ──(отменил после оплаты)─► cancelled [cancelled_by_customer_after_payment] ──► refunded
ready_for_pickup ──(не забрал за pickup-deadline-days)─► cancelled [not_picked_up_in_time] ──► refunded
delivered ──(вернул товар)──────────────────────────────► returned ──► refunded
```

Это полноценная событийная state machine, а не одноразовый случайный
розыгрыш финального статуса: заказ создаётся один раз со `status=new`
и дальше продвигается по реальным правилам (`advance_open_orders`),
переиздаваясь новой строкой при каждом изменении состояния.
`refunded` — не отдельная параллельная ветка, а финансовое разрешение,
наступающее **после** `cancelled` или `returned`, и только если была
успешная оплата (иначе возвращать нечего, `cancelled` терминален).
`cancellation_reason` заполняется в момент первого перехода в
`cancelled` и остаётся заполненным даже после `refunded` — а для
заказов, прошедших `delivered → returned → refunded`, остаётся `NULL`
на всём пути (эта ветка `cancelled` вообще не касается).

Читать историю переходов заказа построчно (кто в какой момент был
`shipped`, потом `ready_for_pickup` и т.д.) из `orders` напрямую
нельзя — `ReplacingMergeTree` физически удаляет старые версии строки
при фоновом мердже, это не event-лог. Но полный **таймлайн вех**
восстановим всегда: каждое переиздание переносит уже достигнутые
milestone-поля (`paid_at`, `shipped_at`, `ready_for_pickup_at`,
`delivered_at`, `cancelled_at`, `returned_at`, `refunded_at`) вперёд —
на актуальной (после `FINAL`) строке видны все пройденные вехи разом.

### Запросы к ClickHouse: FINAL обязателен

Между вставкой переизданной строки и фоновым мерджем `ReplacingMergeTree`
в таблице какое-то время физически лежат **обе** версии заказа —
старая и новая. Наивный `SELECT ... FROM orders GROUP BY status`
в этом окне задвоит заказ сразу в двух статусах. Правильно:

```sql
SELECT status, count() FROM orders FINAL GROUP BY status
```

`FINAL` заставляет ClickHouse разрешить дубликаты по ключу
(`created_at`, `client_id`, `order_id`) в момент запроса, а не ждать
фонового мерджа. Альтернатива — `argMax(status, ingested_at)` с
группировкой по `order_id`, если `FINAL` неприемлем по перформансу.

### Идемпотентная загрузка в ClickHouse

Схема таблиц закоммичена в `clickhouse_schema.sql` (единственный
источник истины — раньше таблицы существовали только в живом
кластере). `load_to_clickhouse.py` применяет её (`CREATE ... IF NOT
EXISTS`) при каждом запуске, поэтому отдельного шага миграции не
требуется.

`write_clickhouse()` делает голый `.append()` — сам по себе он не
защищён от повторной загрузки одного и того же `load_date` (например,
при повторном запуске после сбоя коннектора). Идемпотентность
обеспечивается снаружи, тем же принципом, что commit-маркер в
`generate_data.py`:

- перед загрузкой `load_to_clickhouse.py` проверяет таблицу
  `_load_commits` — если `load_date` там уже есть, скрипт ничего не
  грузит и завершается (no-op), не поднимая даже `SparkSession`;
- `--force-reload` перезаписывает день: сначала `ALTER TABLE ... DROP
  PARTITION` по всем таблицам, партиционированным по `load_date`
  (метаданная операция, не мутация — быстро, без write amplification),
  потом обычная загрузка;
- запись в `_load_commits` — последний шаг, после того как все
  сущности успешно догружены. Если скрипт упадёт раньше — маркер не
  запишется, и следующий запуск честно догрузит день заново.

## Универсальность архитектуры

Разделение по слоям, что здесь переиспользуемо для любого домена, а
что специфично именно для маркетплейса:

**Domain-agnostic (архитектура пайплайна):**
- Hive-style партиционирование и commit-контракт (см. выше) —
  работает для любых сущностей, не только clients/orders/payments.
- DQ-framework в `transform.py` (`add_dq_reason`/`split_valid_invalid`,
  паттерн quarantine-слоя) — набор проверок передаётся списком, не
  привязан к конкретным полям.
- Upsert-паттерн переиздания строк по ключу (заказ/платёж переиздаётся
  новой строкой при изменении состояния, `ReplacingMergeTree` разрешает
  версии по `ingested_at`) — годится для любой сущности с изменяемым
  состоянием: банковского счёта, заявки на кредит, брони отеля.

**Domain-specific (эта конкретная реализация):**
- Схема `generate_data.py` целиком: статусы, дедлайны, причины отмены,
  ready_for_pickup — это глубоко проработанный, но именно
  маркетплейс-специфичный пример поверх универсального движка, а не
  единственно возможный. Для другого домена (банк, сетевая розница)
  схема и state machine писались бы заново, а слой выше — переиспользуется
  как есть.

## Известные ограничения

Осознанно не реализовано в этой версии — для MVP было решено, что
это не окупает сложность прямо сейчас:

- **Нет товарного измерения** (order items, SKU, категории) —
  нельзя тестировать ABC-анализ, cross-sell, category mix.
- **Нет сезонности/трендов** — объём заказов не зависит от дня
  недели или месяца, временные ряды — «белый шум». **Важный побочный
  эффект при агрегации по дню недели:** если диапазон дат генерации не
  кратен 7 дням, некоторые дни недели попадут в выборку на один раз
  больше других (например, 12 понедельников против 11 суббот) — и
  сумма/`COUNT` по дню недели создаст наглядную, но полностью
  искусственную картину различий между днями, хотя почасовое
  распределение (`HOUR_WEIGHTS`) одинаково для всех дней недели без
  исключений. При построении дашбордов/чартов, агрегирующих что-либо
  по дню недели, использовать `AVG` (или
  `COUNT(*) / COUNT(DISTINCT дата)`), а не голый `SUM`/`COUNT` —
  иначе разное число дат на каждый день недели маскируется под
  бизнес-паттерн.
- **Клиенты иммутабельны** — нет SCD2 (смена города, канала и
  т.п.), нет дублей клиентов (одна персона — два `client_id`).
- **Задержек доставки нет** — время в пути всегда строго меньше
  `--delivery-deadline-days`/`--pickup-deadline-days`. Можно добавить
  отдельным шагом позже.
- **Батч — календарный день, не час.** Короткий (например, часовой)
  `--payment-deadline-hours` создаёт заметную задержку между реальным
  моментом события (клиент не оплатил) и его появлением в выгрузке
  (только на следующий день) — timestamps при этом остаются точными,
  страдает только свежесть данных, не их корректность. Переход на
  батчи чаще раза в день — самостоятельная архитектурная задача
  (другой commit-контракт, другая партиционная схема), не покрыта
  этой версией.
- **Seed зависит только от `--load-date`**, не от остальных
  параметров запуска — прогон одной и той же даты с другим
  `--clients-count` даёт другую случайность, но повторный прогон с
  идентичными параметрами полностью детерминирован.
- **`load_existing_clients` перечитывает всех исторических
  клиентов при каждом запуске** — с ростом истории (сотни
  `load_date`) время старта будет расти линейно. Для объёма MVP
  это не проблема; при росте истории потребует индекса/кэша.
  `load_existing_orders`, в отличие от клиентов, эту проблему уже не
  имеет — глубина скана там ограничена явно.
- **Доля отмен/возвратов искусственно падает в последние ~34 дня
  выгрузки (right-censoring).** `advance_open_orders` — событийная
  state machine: заказ продвигается к `cancelled`/`returned`/
  `refunded` только за счёт последующих ежедневных запусков
  генератора, «будущего» после последнего `load_date` не существует.
  `compute_lookback_days()` суммирует все дедлайны состояний
  (оплата, отправка, доставка, забор, окно возврата, обработка
  рефанда) и даёт ≈34 дня — горизонт, после которого судьба заказа
  гарантированно определена. Заказы, созданные позже этого горизонта
  до последнего `load_date`, ещё не успели «дозреть» до отмены или
  возврата и висят в промежуточных статусах — при агрегации доли
  отмен/возвратов по дате создания заказа это выглядит как
  снижающийся тренд к концу периода, хотя реальная склонность к
  отменам не изменилась. При построении такой метрики — либо
  отбрасывать последние ~34 дня перед `max(load_date)`, либо считать
  на фиксированном окне созревания (% заказов, отменённых/возвращённых
  в течение N дней с момента создания), а не «на сегодня».

```bash
pip install -r requirements-dev.txt

```

Тесты сфокусированы на местах, которые реально ломались в процессе
