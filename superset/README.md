# Правки дашборда «Аналитика маркетплейса»

`apply_review_fixes.py` применяет к Superset правки P0/P1/P2 из ревью
дашборда: переводит датасеты на витрины ClickHouse, правит form_data
чартов, раскладку и метаданные дашборда через REST API.

SQL витрин в этом скрипте нет — он живёт в `clickhouse_marts.sql`
(база `marketplace_marts`) и применяется загрузчиком, см. «Семантический
слой» в корневом README. Скрипт только переключает датасеты Superset на
готовые витрины: `sql=None`, схема `marketplace_marts`. Датасет при этом
не пересоздаётся и не переименовывается, поэтому чарты, ссылающиеся на
него по id, продолжают работать.

**Порядок важен:** витрины должны быть в ClickHouse раньше, чем скрипт
переведёт на них датасеты. Достаточно одного прогона
`load_to_clickhouse.py` — он применяет их при любой загрузке, включая
no-op на уже загруженный день.

Скрипт идемпотентен — повторный запуск приводит инстанс в то же
состояние, а не накапливает изменения. По умолчанию он ничего не пишет,
а печатает план.

## Запуск

```bash
pip install -r requirements-superset.txt

python superset/apply_review_fixes.py --url http://superset.example.com:8088 \
    --username admin --phases p0,p1,p2
```

Зависимость одна — `requests`; она вынесена отдельным файлом и
намеренно не тянет `requirements.txt`: скрипт ходит по HTTP и не
трогает данные, pandas и pyspark ему не нужны. Для воспроизводимой
установки есть `requirements-superset.lock` с хешами.

### Запуск без участия человека

Чтобы скрипт мог работать сам — из планировщика или из чужой сессии —
положи креды в файл, который он прочитает:

```bash
mkdir -p ~/.superset && cat > ~/.superset/credentials.json <<'JSON'
{"url": "http://localhost:8088", "username": "superset_admin", "password": "..."}
JSON
chmod 600 ~/.superset/credentials.json
```

Скрипт откажется читать файл, доступный кому-то кроме владельца: файл с
паролем, который виден всем, — это не защита, а её видимость.

Порядок источников: аргумент командной строки, потом переменная
окружения, потом файл. Пароль не передаётся ни аргументом (виден в
списке процессов), ни без нужды окружением.

### Удаление чартов

```bash
python superset/apply_review_fixes.py --delete-charts 44,45,46 --apply
```

Только по явному списку id и только тех, на которые не ссылается
раскладка дашборда, — опечатка в списке не снесёт рабочий чарт. Без
`--apply` печатается список к удалению.

Пароль скрипт спросит скрытым вводом. Передавать его в командной строке
не нужно: оттуда он попадает в историю оболочки и в список процессов.
Для CI, где спрашивать некого, остались `SUPERSET_PASSWORD` и
`--password`; если пароля нет, а ввод или вывод перенаправлены, скрипт
скажет об этом и выйдет, а не повиснет на приглашении.

Показанное выше — только план. Чтобы записать изменения, добавь
`--apply`.

В PowerShell перенос строки — обратная кавычка, а не `\`, и питон
удобнее звать из venv:

```powershell
.\venv\Scripts\python.exe superset\apply_review_fixes.py --url http://superset.example.com:8088 --username admin --phases p0,p1,p2
```

Фазы можно применять по одной (`--phases p0`), но порядок важен:
чарты фазы p1 опираются на колонки, которые появляются в витринах на
фазе p0.

Перед первой записью скрипт выгружает текущее состояние в
`superset_backup_<timestamp>.zip`. Это путь отката: импорт этого ZIP
через UI (Dashboards → Import) или `POST /api/v1/dashboard/import/`
с `overwrite=true` возвращает дашборд в исходный вид.

## Что делает

| Фаза | Правки |
| --- | --- |
| `p0` | Перевод датасетов на витрины (FINAL, словари, `is_mature`), GMV и средний чек только по оплаченным заказам, отсечение незрелого хвоста, распределение времени до первого заказа вместо среднего, перцентили рефанда по сырым длительностям, сортировка «топ-10» и разбивки DQ |
| `p1` | нативная воронка, горизонтальные бары, подписи пирогов, проценты вместо долей, границы оси success rate, скользящее среднее за 7 дней, порядок перцентилей, русские названия вкладок и заголовков |
| `p2` | фильтры периода / города / канала, KPI-строка на обзоре, свежесть загрузки на вкладке качества, палитра и автообновление |

## Что скрипт не делает

- **Конверсия.** Скрипт ограничивает её зрелой когортой, но сам по
  себе неконвертящихся клиентов не создаёт: если данные сгенерированы
  без `--never-order-rate`, заказ есть у каждого, и метрика честно
  покажет 100%. На текущем стенде данные перегенерированы, конверсия —
  около 74%.
- **Ось дней недели.** Переворот задаётся ключом `sort_y_axis`,
  имя которого зависит от версии Superset. Если понедельник остался
  внизу — поправить в UI чарта.

## Из чего собран стенд

Конфигурация стенда лежит в `deploy/`: `nginx-marketplace-analytics.conf`,
`docker-compose.yml`, `Dockerfile` и `superset_config.py`. В каждом файле
первой строкой написано, куда он кладётся на сервере.

Секретов в них нет — пароль postgres и `SECRET_KEY` подаются файлами из
`/opt/superset/secrets`, которого в репозитории нет и не должно быть.

Эти четыре файла живут вне рабочей копии проекта, поэтому выкладка через
git их не обновляет: правку надо перенести руками в обе стороны.
Разошлись или нет — видно по `md5sum`.

## Как код попадает на стенд

Копия проекта на сервере — приёмник, а не рабочее место: правки едут
туда с машины разработчика одной командой.

```bash
git push server master
```

`server` — это адрес каталога проекта на сервере по SSH, заведённый
рядом с `origin`. Обычно рабочая копия push не принимает, здесь это
разрешено настройкой `receive.denyCurrentBranch = updateInstead`: она
обновляет и историю, и сами файлы, но только если в рабочем каталоге
нет несохранённых правок. Отказ означает, что на сервере кто-то правил
файлы руками, — и это ровно то, о чём стоит узнать до выкладки, а не
после.

Копировать файлы по одному (`scp`) не надо, даже когда правка в одну
строку. Содержимое от этого окажется верным, а история на сервере — нет:
git будет считать, что там лежит прежняя версия, и любая команда «верни
как записано» молча откатит стенд на неё же. Заодно такая правка
блокирует нормальную выкладку, потому что делает рабочий каталог
грязным.

Airflow читает DAG по симлинку из этого же каталога, поэтому отдельно
выкладывать его не нужно.

## Как стенд отдаётся наружу

```
браузер → https://marketplace-analytics.andrewsalmin.com  (nginx, Let's Encrypt)
                        ↓ proxy_pass
              http://127.0.0.1:8088                       (gunicorn в контейнере)
```

Короткий вход `andrewsalmin.com/marketplace-analytics` отдаёт 301 на
поддомен. Поддомен, а не подпуть, вынужденно: в этой сборке Superset нет
ни `SUPERSET_APP_ROOT`, ни `APPLICATION_ROOT`, поэтому он всегда строит
ссылки на статику и API от корня. На подпути они улетали бы мимо, и
лечится это только переписыванием URL в nginx — хрупко и разъезжается
при обновлении.

Две настройки, без которых схема работает неправильно и незаметно:

- **`--bind 127.0.0.1:8088`** в `docker-compose.yml`. Контейнер запущен
  с `network_mode: host`, поэтому привязка к `0.0.0.0` означала, что
  Superset торчит наружу по голому HTTP в обход прокси — и пароль
  администратора при входе идёт открытым текстом. Postgres и Redis в
  том же файле привязаны к петле изначально; Superset из этого правила
  выпадал.
- **`ENABLE_PROXY_FIX = True`** в `superset_config.py`. nginx передаёт
  `X-Forwarded-Proto`, но без этого флага Superset заголовку не верит и
  считает, что его открыли по http.

## Секреты стенда

Пароль к Postgres и `SECRET_KEY` передаются контейнерам файлами, а не
переменными окружения:

```yaml
secrets:
  postgres_password:
    file: ./secrets/postgres_password
  superset_secret_key:
    file: ./secrets/superset_secret_key
```

Переменная окружения видна в `docker inspect` любому, у кого есть доступ
к докеру, лежит в `/proc/<pid>/environ`, наследуется дочерними
процессами и попадает в вывод, который люди вставляют в переписку не
глядя. Файл читает только тот процесс, которому он смонтирован, и только
в тех контейнерах, где объявлен.

`superset_config.py` читает их через `_secret()` с откатом на прежние
переменные: если файла нет, сервис поднимется по старой схеме, а не
упадёт с невнятной ошибкой подключения.

**Права выставлены не так, как подсказывает первый инстинкт.** Файлы
имеют режим 644, защищает их каталог `secrets/` с режимом 700. Причина в
том, что один и тот же `postgres_password` читают два контейнера под
разными пользователями — `postgres` (uid 999) и `superset` (uid 1000), —
и владельцем можно сделать только одного из них. Режим 600 приводит к
`Permission denied` при старте: Superset падает на чтении секрета, а в
логе видна только «Worker failed to boot».

На хосте это не ослабление: посторонний пользователь не пройдёт внутрь
каталога, а `sudo` прочитал бы файл при любых правах.

Проверить, что значений в окружении не осталось:

```bash
sudo docker inspect superset --format '{{range .Config.Env}}{{println .}}{{end}}'   | grep -E 'PASSWORD=|SECRET_KEY=|SQLALCHEMY_DATABASE_URI='   # должно быть пусто
```

Прежний `.env` удалён: значения живут в `secrets/`, и держать вторую
копию тех же секретов рядом — лишний способ их потерять.

## Права анонимного посетителя

Дашборд открыт без логина, поэтому роль `Public` — это граница между
«показать работу» и «отдать наружу лишнее». Приводится к точному
составу отдельной командой:

```bash
python superset/apply_review_fixes.py --narrow-public Public          # план
python superset/apply_review_fixes.py --narrow-public Public --apply  # запись
```

Команда отдельная, а не часть обычного прогона, намеренно: снятие прав
опаснее выдачи, и делать это мимоходом нельзя. Перед записью снимается
снимок роли в `superset_role_Public_<время>.json`, после записи состав
сверяется с ожидаемым.

Набор считается с нуля, а не «текущее минус подозрительное»:

- **датасеты** — те, которые реально используют чарты этого дашборда;
  список берётся из самих чартов, потому что перечень в коде рассохнется
  при первом же новом графике;
- **функциональные права** — пять штук, перечисленные в
  `PUBLIC_REQUIRED_PERMISSIONS`, каждое с причиной.

Что было снято и почему:

| Снято | Чем было плохо |
|---|---|
| `schema_access on [...].[marketplace_analytics]` | ковровый доступ ко всей сырой схеме: карантинные таблицы, `dq_metrics`, `_load_commits` |
| `can_read on Dataset` | `GET /api/v1/dataset/` отдавал описания датасетов вместе с SQL виртуальных |
| `can_explore_json on Superset` | legacy-эндпоинт данных; дашборд ходит в `/api/v1/chart/data` |
| `can_get on Datasource`, `can_external_metadata on Datasource` | служебные для конструктора чартов, посетителю не нужны |
| доступ к двум датасетам | ни один чарт дашборда их не использует |

Взамен выданы точечные права на четыре датасета, которые раньше
работали только благодаря ковровому `schema_access`.

Проверять после сужения нужно **обязательно и глазами**: код ответа 200
на странице дашборда ничего не доказывает — при нехватке прав она
отдаётся, но чарты остаются пустыми. Снимок делается без логина:

```bash
google-chrome --headless --disable-gpu --no-sandbox   --window-size=1600,1000 --virtual-time-budget=90000   --screenshot=/tmp/check.png 'http://localhost:8088/superset/dashboard/1/'
```

Заодно проверяется, что закрытое осталось закрытым — оба должны
отвечать 401:

```bash
curl -s -o /dev/null -w '%{http_code}
' http://localhost:8088/api/v1/dataset/
curl -s -o /dev/null -w '%{http_code}
' http://localhost:8088/api/v1/database/
```

## Выводы на обзоре

Блок «Что видно в данных» — утверждения с периодом, числом и указанием,
где каждое перепроверить. Формулировки лежат в `overview_findings.py`,
**числа туда не вписаны**: они считаются по данным при каждом
применении правок — и в том числе ночью, задачей `refresh_dashboard`
в конце ежедневного пайплайна. Данные прирастают каждую ночь, поэтому
и текст обновляется тогда же.

Так сделано потому, что числа относятся к периоду данных и после
перегенерации меняются. Написанные руками, они устаревали бы молча — на
обзоре осталось бы уверенное утверждение с точностью до десятой
процента, которое из данных больше не следует. Читатель его проверит,
там для этого сказано где, и расхождение подорвёт доверие ко всему
остальному на экране.

Посмотреть, что получится, не трогая дашборд:

```bash
python overview_findings.py
```

Если ClickHouse недоступен — например, скрипт запущен с ноутбука, —
прежний текст остаётся нетронутым и об этом печатается предупреждение:
показать устаревшие числа плохо, но затереть их заглушкой хуже.

Причинности в выводах нет намеренно. Сказать «канал X самый выгодный»
нельзя, не зная расходов на привлечение, а таких данных в модели нет
вовсе: это было бы не выводом, а догадкой, поданной с точностью до
десятой доли процента. Запрет закреплён тестом — он падает на словах
вроде «выгоднее», «рентабельнее», «из-за».

## Язык дашборда и язык кода

Подписи на дашборде намеренно не повторяют терминологию репозитория:
их читает тот, кто смотрит на цифры, а не тот, кто чинит пайплайн.
Соответствие между тем и другим — здесь.

| На дашборде | В коде и в этом репозитории |
|---|---|
| «Каждый платёж считается один раз, по последнему состоянию» | дедупликация `FINAL` по `ReplacingMergeTree`, см. корневой README |
| «Отклонено при загрузке», «отклонённые строки» | карантин: `quarantine_*`, правила в `transform.py` |
| «Найдено ошибок» | срабатывания DQ-правил, таблица `dq_metrics` |
| «Доля отклонённых строк по дням» | `invalid_rows / total_rows` из `dq_metrics` |
| «Сообщение о закрытии заказа было отклонено проверками» | закрывающая строка ушла в карантин, последней валидной осталась открытая |
| «Отставание данных» | `max(hours_since_load)` из витрины `load_freshness` |
| «Старше 34 дней» | горизонт зрелости `maturity_days()` из `growth_config.json` |

Правило простое: в названии чарта, его описании и подписях осей не
должно быть ни имён колонок, ни ключевых слов SQL, ни наших внутренних
слов вроде «карантин» и «сущность». Всё это остаётся в коде и в
README — там оно на своём месте и никому не мешает.

## Настройки самого инстанса

Две вещи скрипт задать не может — они живут в `superset_config.py` на
сервере (в нашем стенде это `/opt/superset/superset_config.py`,
примонтированный в контейнер) и требуют перезапуска Superset.

```python
# Разделители чисел. Без этого «237,5 млн ₽» выглядит как «237.5»,
# а «137 104» — как «137,104».
D3_FORMAT = {
    "decimal": ",",
    "thousands": " ",
    "grouping": [3],
}

# Список языков — не перевод, а именно список.
LANGUAGES = {
    "en": {"flag": "us", "name": "English"},
    "ru": {"flag": "ru", "name": "Russian"},
}
```

`LANGUAGES` выглядит необязательным, но его отсутствие роняет дашборд
целиком, и разбираться в этом дорого. Фронтенд берёт язык из настроек
браузера (`navigator.language`) и ищет его в этом списке. У браузера с
русским языком запись `ru` не находится, `languages["ru"].flag` читается
у `undefined` — и падает инициализация всего приложения. На экране
чёрная страница без единой надписи, в логах сервера чисто, запросы
данных отвечают 200. Видно только в консоли браузера.

Перевода это не даёт: языкового пакета `ru` в сборке Superset нет,
`/superset/language_pack/ru/` отвечает 404, интерфейс остаётся
английским. Запись нужна ровно затем, чтобы фронтенду было что найти.
По той же причине роли Public выдано право `can_language_pack` — иначе
анонимный посетитель получает на этот запрос HTML страницы логина
вместо JSON, разбор падает, и чарты снова перестают рисоваться.

Единицы измерения (`млн ₽`, `₽`) задаются подписью карточки в
`KPI_CHARTS`, а не полем валюты Superset: то принимает код ISO и
печатает «RUB», потому что символ берётся из локали фронтенда. Передать
туда «₽» нельзя — `Intl` не знает такого кода и молча выбрасывает
суффикс вместе с валютой.

## Проверка после применения

1. Воронка: «Создано» должно заметно просесть — незрелые заказы больше
   не считаются. Горизонт зрелости берётся из `growth_config.json` как
   сумма всех дедлайнов (на дефолтах 34 дня), тот же расчёт, что в
   `compute_lookback_days()` генератора: до его истечения заказ ещё
   может отмениться или вернуться.
2. «Способы оплаты и статус»: «Успешно» должно упасть примерно на число
   возвратов — это и есть эффект FINAL.
3. Доли отмен и возвратов: правый край больше не падает в ноль.
